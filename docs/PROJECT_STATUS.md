# SofDom: статус аудита и приоритеты

Последняя сверка: 2026-10-22. Этот документ — долговременная точка продолжения работ по качеству данных и локальной стабильности SofDom. Он дополняет технические документы, но не заменяет проверку текущего Git-состояния и исходников.

## Правила работы

- Работать по одному приоритету: завершить изменение, проверить код и тесты, обновить этот документ, затем переходить дальше.
- Владелец задачи (оркестратор) анализирует требования, проверяет исходники, отчёт агента, diff и результаты тестов. Код реализации поручается отдельному агенту.
- Агент до изменений проверяет `git status`, staged/unstaged diff и последние коммиты; не затрагивает `rea`, базу и иные пользовательские файлы; не применяет `git add .`, `git reset`, `git checkout`, `git clean`; не пушит.
- Перед каждым этапом создать именованную локальную точку возврата на текущем HEAD, если имя не занято. Не утверждать, что тег сохраняет незакоммиченные изменения.
- После этапа записать в этот документ: что проверено, что изменено, коммит/тег, тесты и их фактический результат, остаточные риски. Не включать секреты.
- Не обходить CAPTCHA/anti-bot ограничения. Использовать допустимые источники и соблюдать их правила.

**Где хранятся фото сейчас:** в изученных путях сбора изображения сохраняются преимущественно как URL, а не как скачанные локальные файлы. Парсер извлекает ссылки CDN Авито, `fullUrl` Циан и URL галерей БезПосредников. Проверенный ingest-путь не скачивает и не архивирует байты изображений локально: браузер загружает их по ссылкам источников/CDN. В проектной архитектурной диаграмме упомянут «кэш и прокси изображений», но наличие реального рабочего компонента необходимо отдельно подтвердить, не полагаясь на диаграмму.

### 2. Геолокация и происхождение геоданных — в проверке

**Подтверждённые ранее риски и их устранение:**

- `backend/scraper.py`: устранено присвоение фиктивной точки центра Томска (`56.4977, 84.9744`) для Авито и БезПосредников. Если у карточки нет подтверждённых координат от источника, сохраняются `lat=None, lng=None, geo_precision='none'`.
- `backend/scraper.py`: для Циан (регион 4620 Томская область) добавлена проверка реального населённого пункта (`detect_city`) и района (`detect_tomsk_district`). Объекты вне Томска (Колпашево, Северск и др.) не маркируются городом 'Томск' и не получают районы Томска. Подлинные координаты от источника сохраняются с `geo_precision='exact', geo_source='cian'`.
- `backend/db.py:enrich_tomsk_geo()`: полностью удалена генерация псевдокоординат со смещением через `hash(id)`. Исключён безусловный fallback на 'Советский район'. Нормализация стала 100% детерминированной и идемпотентной.
- Выделен модуль `backend/geo_utils.py` с чистыми утилитами классификации координат, валидации населённого пункта, сопоставления районов, вычисления spatial bounding box (`calc_radius_bbox`) и диагностическим конвертом агломерации `TOMSK_AGGLOMERATION_ENVELOPE`.
- Воспроизведён и закрыт кейс `SD-1075` (Колпашево): на тестовой базе проверено, что город определяется как 'Колпашево', ошибочный 'Советский район' очищается, координаты сохраняются как точные для Колпашево.
- В SQLite схему `apartments` добавлены поля `geo_precision` (`'exact'`, `'approximate'`, `'unknown'`, `'none'`), `geo_source` и `geo_observed_at TIMESTAMP` с поддержкой мягкой миграции (`ALTER TABLE ADD COLUMN` в `init_db()`).
- В `backend/db.py:upsert_apartment()` обеспечен строгий инвариант достоверности (provenance):
  * Если координаты невалидны или отсутствуют, метаданные гарантированно сбрасываются в `geo_precision='none', geo_source='none', geo_observed_at=None`. Внешняя попытка передать `geo_precision='exact'` при отклонённых координатах принудительно нейтрализуется.
  * В `ON CONFLICT(id) DO UPDATE SET` координаты и метаданные обновляются безусловно из `excluded.*`. Устранён дефект оркестратора (a), когда устаревшие точные координаты оставались в базе при обновлении объявления с `lat=None, lng=None`.
  * Устранён дефект оркестратора (b), когда при `lat=95, lng=200` в базу записывался `lat=NULL`, но сохранялись метаданные `exact/caller`.
  * Синтетические координаты Авито и БезПосредников (включая старый джиттер) строго отклоняются (`clean_lat=None, clean_lng=None, precision='none'`).
- В `backend/db.py:list_apartments_geo()` реализован spatial pre-filter (`calc_radius_bbox` в SQL):
  * При поиске по радиусу SQL-запрос фильтрует объекты по bounding box до применения `LIMIT`. Это устраняет дефект вытеснения близких объектов дешёвыми удалёнными квартирами из других районов.
  * Если `radius_km` передан без координат центра (`center_lat=None, center_lng=None`), радиусная фильтрация не применяется, ошибка не выбрасывается, а `distance_km` возвращается как `None`.
- В локальном fallback фронтенда (`frontend/src/services/mapService.ts`):
  * Объекты из `TOMSK_MAP_FALLBACK` и `OFFERS` без подтверждённой provenance больше не получают `exact` по умолчанию: они помечаются как `unknown` (`is_approximate: true`).
  * Для них не вычисляется фиктивное расстояние (`distance_km: null`), и они исключаются из точного поиска по радиусу (`params.radius_km`).
  * TypeScript-типы в `frontend/src/types/index.ts`, `frontend/src/services/mapService.ts` и `admin/src/data/types.ts` согласованы со значением `'unknown'`.
- Сторонние внешние геокодеры не подключались, ключи и адреса наружу не передаются. Рабочая база `backend/realty.db` не запускалась и не модифицировалась (все проверки выполнены на временных базах).

- Проверка миграции старой SQLite базы на лету — успешно протестирована в unit-тесте.

**Разграничение уровней точности (provenance):**
- `'exact'`: подлинные координаты от подтверждённого источника (Циан), прошедшие валидацию внутри конверта Томска. Участвуют в радиусном поиске с вычислением расстояния.
- `'approximate'`: поддерживается архитектурно на уровне схемы БД, API и UI (для центроидов районов), но текущие продакшен-парсеры его НЕ генерируют (возвращают `none`). Не имеет расстояния в км и не участвует в радиусном поиске.
- `'unknown'`: локальный offline-fallback каталог фронтенда без проверенной привязки к местности. Исключён из радиусного поиска.
- `'none'`: координаты отсутствуют, невалидны или были синтетическими заглушками/джиттером. Такие объекты доступны в фильтрах каталога, но исключаются из карты.

### 3. Актуальность объявлений, дедупликация и происхождение — не закрыт

Ранее аудит отметил хрупкий HTML-разбор Авито, отсутствие надёжного жизненного цикла удаления/истечения объявления после неполной синхронизации и слабые межплощадочные совпадения `cross_matcher.py` (адрес/цена вместо подтверждённой связи с первоисточником). Перепроверить текущую реализацию перед выводами и изменениями. Не склеивать объявления и контакты между площадками только по похожему адресу/цене. Зафиксировать идентификатор источника, исходный URL, время наблюдения и основание совпадения; неполный/ошибочный сбор не должен помечать массово объявления как снятые.

### 4. Устойчивость и безопасность работы на Mac — не закрыт

Целевая установка владельца: пока без покупки сервера, Mac будет оставаться включённым. Локальный режим возможен, но доступность зависит от питания, сети и сна; сам факт работающего Mac не обеспечивает публичный доступ к локальному API. Ранее аудит отметил, что `start_live.sh` запускает API/туннель, но не гарантирует запуск непрерывного сборщика; обычный CLI harvester ограничен одной итерацией; API слушает `0.0.0.0`, а туннель может раскрывать сервис наружу. Повторно проверить эти точки перед рекомендацией.

Цель будущего этапа: локальный контролируемый supervisor/расписание, health/status, логи и ротация, ограниченные повторы с backoff, сохранение состояния, резервное копирование и проверенное восстановление SQLite, явный localhost-only режим по умолчанию, документированный ручной запуск/останов. Никакого широкого `pkill`; не публиковать API через туннель без отдельной необходимости и контроля доступа. Не заявлять «24/7», пока нет наблюдаемых health-check и теста восстановления.
