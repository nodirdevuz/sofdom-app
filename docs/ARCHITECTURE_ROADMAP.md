# Архитектурный план SofDom: надёжность, скорость и рост

Дата исходной оценки: 2026-10-22. План рассчитан на текущую цель: один Mac, локальное backend-приложение, SQLite и сбор данных из нескольких внешних источников. Это не утверждение, что все перечисленные механизмы уже реализованы.

## Главный принцип

Не строить «большую архитектуру» заранее. Сначала обеспечить восстановление, корректность данных и наблюдаемость; затем измерить реальную нагрузку и оптимизировать конкретные медленные операции. Реплики, шардинг, отдельный брокер сообщений, WebSocket и CQRS не являются обязательными условиями надёжной локальной системы.

Порядок работ:

1. Восстановление после сбоя и безопасная эксплуатация.
2. Надёжный цикл синхронизации и корректная запись данных.
3. Наблюдаемость и измерение производительности.
4. Оптимизация SQLite и запросов.
5. Кэш чтения и обновление интерфейса в соответствии с требованиями свежести.
6. Очередь/worker только если фоновые задачи должны переживать перезапуск или начинают мешать API.
7. Отдельная read-модель/CQRS и смена хранилища только при измеримом ограничении SQLite.

## P0. Защита данных и восстановление

**Цель:** после ошибки, перезагрузки Mac или повреждения файла можно понять состояние и восстановить последний согласованный снимок.

- Определить единый безопасный каталог данных для SQLite, логов и локальных медиа. Не хранить рабочие данные внутри `dist`, не включать их в Git и не полагаться на временные каталоги.
- Настроить резервное копирование SQLite через SQLite Backup API или согласованный snapshot, а не копировать только основной файл во время активного WAL.
- Хранить несколько поколений резервных копий с датой, проверять результат резервирования и регулярно выполнять пробное восстановление во временный файл.
- Вести журнал запусков синхронизации: `run_id`, источник, время начала/окончания, статус, найдено/обработано/записано/ошибок, последняя успешная синхронизация. Не включать секреты, cookies, телефоны и полные приватные ответы в логи.
- Добавить health/status-проверку, показывающую состояние API, БД и последней синхронизации. «Процесс запущен» не равно «данные обновляются».
- Сделать запуск локальным и ограниченным `127.0.0.1` по умолчанию; отдельно документировать любое внешнее раскрытие API. Публичный туннель не включать автоматически.
- Проверить конфигурацию Mac: сон/питание/перезапуск, права доступа к каталогу данных, свободное место. Это операционная настройка владельца, а не гарантия кода.

**Критерий готовности:** документированный запуск/останов; резервная копия создаётся и проверяется; восстановление в отдельный временный файл проходит тест; после искусственно прерванной синхронизации виден её незавершённый статус, а данные остаются согласованными.

## P1. Надёжный сбор и запись

**Цель:** сбой одного сайта или процесса не приводит к повреждению БД, потере других источников или ложному снятию объявлений.

- Сохранять успешный результат каждого источника независимо; отказ одного источника не должен отменять уже полученные корректные результаты других.
- Сначала полностью получить/валидировать порцию источника, затем записывать её короткой SQLite-транзакцией. Избегать `commit` на каждую запись. Подобрать разумный размер транзакции, чтобы она не удерживала блокировку во время сетевых запросов.
- Сохранять уникальность по стабильному ID источника и использовать upsert как идемпотентную операцию.
- Разделить «объявление не пришло в этом запуске» и «объявление достоверно снято». Снимать/архивировать запись только после успешного полного прохода источника и явной политики устаревания.
- Не перезаписывать подтверждённые поля пустыми или неполными ответами. При неуспешном/урезанном сборе сохранить предыдущие корректные значения и явно записать статус/ошибку запуска.
- Защитить синхронизацию локальным lock от параллельного запуска вручную, из API и расписания.
- Сетевые повторы: только для временных сетевых ошибок/ограниченных 5xx; экспоненциальный backoff с jitter, лимит числа попыток и общий deadline. Не повторять 4xx/блокировки бесконечно и не обходить защиту площадки.
- Circuit breaker можно добавить позже как состояние на источник: при серии временных ошибок временно приостанавливать обращения и сообщать оператору. Не применять его как механизм обхода ограничений.

**Критерий готовности:** повторный запуск не создаёт дублей; частичный сбой одного источника не портит другие данные; транзакция атомарна; параллельный запуск предотвращён; тесты имитируют сетевые ошибки и перезапуск.

## P2. Наблюдаемость и измерения

**Цель:** определять, что именно медленно или ломается, прежде чем вводить кэш, индексы или очередь.

- Записывать длительность по этапам и источникам: получение, разбор, нормализация, запись.
- Собирать счётчики успехов/ошибок, количество новых/обновлённых/пропущенных объявлений, число записей без координат/фото, возраст последнего успешного сбора.
- Вести структурированные логи с уровнем и ротацией; сетевые ошибки должны быть видны, а не замалчиваться.
- Измерить наиболее частые и тяжёлые SQL-запросы, размер таблиц/БД, время синхронизации и API latency на типичной локальной нагрузке.
- Подготовить маленькие повторяемые тестовые данные и сценарий измерения; не использовать реальные секреты/персональные данные в тестах.

**Критерий готовности:** можно ответить на вопросы «когда источник обновлялся последний раз», «почему не обновился», «сколько времени занял запуск» и «какой запрос тормозит».

## P3. SQLite и запросы

**Цель:** улучшить локальную скорость без лишней инфраструктуры.

- WAL уже включён в `backend/db.py`. Проверить и документировать разумный `busy_timeout`, безопасное завершение и контроль размера WAL/checkpoint; не включать настройки вслепую.
- Проверить все реальные `WHERE`, `ORDER BY`, `JOIN` и ограничения внешних ключей. Для кандидатов исследовать `EXPLAIN QUERY PLAN` на копии/временной БД и добавить только индексы, улучшающие измеренные запросы.
- Рассмотреть индексы на таблицах связей для частых запросов по `user_id`, `apartment_id`, статусу/сроку подписки, а также индекс объявлений под подтверждённые фильтры/сортировки. Не создавать индексы без подтверждённого шаблона запроса.
- Проверить пагинацию и верхние лимиты API; не загружать большие таблицы целиком без необходимости.
- Не шардировать SQLite для текущего масштаба. Шардинг усложнит согласованность, резервирование и запросы; сначала измерить, что один файл действительно стал узким местом.
- Не добавлять реплики чтения в SQLite локального приложения без подтверждённой конкуренции читателей/писателей и плана синхронизации реплики.

**Критерий готовности:** до/после замер, планы запросов, тесты на временной БД, без ухудшения записи и без миграции рабочей базы прямо во время разработки.

## P4. Кэширование и свежесть

**Что уже найдено в коде при аудите 2026-10-22:**

- `frontend/src/services/mapService.ts` содержит кэш карты в памяти с TTL 10 минут и возвращает локальный fallback при недоступном API.
- В `getCacheKey()` нужно перепроверить полноту ключа: некоторые параметры запроса могут отсутствовать. Кэш-ключ обязан учитывать все поля, влияющие на ответ (включая цену, bbox, фильтры и местоположение/радиус), иначе возможен возврат результата от другого фильтра.
- При попадании в действующий кэш функция возвращает ответ, не отправляя фоновое обновление. Поэтому свежесть ограничена TTL.
- `frontend/src/lib/geocode.ts` содержит клиентский кэш геокодирования и coalescing одинаковых одновременных запросов. Это кэш геокодера, не объявлений.
- Серверного кэша объявлений и Redis-кластера для текущего локального режима не обнаружено.

**План:**

- Сначала исправить полноту cache key и добавить тесты на пары запросов, отличающиеся одним фильтром.
- Определить допустимую свежесть по типам данных. Не использовать один TTL для карты, списка, контактов и геокодирования.
- Если нужна более свежая карта, использовать stale-while-revalidate: быстро показать ещё пригодный кеш, запустить ровно один фоновый запрос на ключ и заменить данные после успеха. На ошибке оставить stale-данные с видимым статусом/временем обновления.
- Ограничить размер и время жизни памяти-кэша. Не кешировать персональные/авторизованные ответы общим ключом.
- Backend-кэш добавлять только если измерения показали повторяющиеся дорогие чтения. Для одного локального процесса начать с ограниченного in-memory кэша и явной инвалидации после успешной синхронизации; Redis не нужен без нескольких процессов/машин.

**Критерий готовности:** фильтры не «перетекают» между кешированными ответами; ошибки API не выглядят как успешное обновление; freshness и время последнего обновления видны.

## P5. Долгие задачи и обновления UI

**Очередь задач:**

- Текущий FastAPI `BackgroundTasks` подходит только для короткой best-effort работы в том же процессе. Он не является durable queue и задача может потеряться при остановке/падении процесса.
- Для одного Mac сначала рассмотреть отдельный процесс-сборщик с расписанием, локальной блокировкой, SQLite status table и восстановлением «запуск был прерван». Это проще, чем брокер.
- Перейти к durable queue/worker только если появились несколько независимых долгих задач, необходимость переживать рестарт с гарантированным выполнением, параллельные рабочие потоки или наблюдаемая очередь ожидания.
- Любая задача должна иметь ID, статус, время запуска/окончания, ограниченные повторы и идемпотентную обработку.

**WebSocket/SSE/Long polling:**

- Сейчас REST достаточен для интерфейса, который обновляется с заданным интервалом или после явного запроса.
- WebSocket не делает сбор источников быстрее и добавляет соединения, reconnect, heartbeat, авторизацию и контроль backpressure.
- Если появится измеримое требование показывать новые объявления сразу нескольким открытым клиентам, начать с SSE для однонаправленных уведомлений; WebSocket выбирать при реальном двунаправленном обмене. Иначе оставить REST + polling.
- Long polling рассматривать только при ограничениях окружения, где обычный polling и SSE не подходят.

**Критерий перехода:** измеренная задержка/потеря задач или чёткое требование продукта, а не архитектурная мода.

## P6. CQRS и горизонтальное масштабирование

- Сейчас чтение и запись используют один SQLite datastore; отдельные CQRS-модели не обнаружены.
- CQRS добавляет рассинхронизацию read model, обработку событий, повторное построение индексов и более сложную диагностику. Для одного Mac преимуществ пока не доказано.
- Сначала разделить кодовые функции чтения/записи и контракты API без отдельной инфраструктуры. Это улучшит тестируемость, но само по себе не означает CQRS.
- Реальный переход к отдельной read-модели или другой СУБД обсуждать только после метрик: конкурирующие нагрузки, блокировки SQLite, неприемлемая задержка запроса, объём данных/запросов, который не удаётся решить индексами и пагинацией.
- Шардинг, реплики и брокер сообщений — отдельное решение с планом восстановления, мониторинга и обслуживания; не добавлять для гипотетических «тысячи клиентов», если продукт работает локально на одном Mac.

## Соответствие шести принципам

| Принцип | Состояние на дату оценки | Разумный следующий шаг |
|---|---|---|
| Кэш/индексы/реплики для чтения | Клиентский map-cache и geocode-cache есть; вторичные SQL-индексы не подтверждены; backend read-cache и реплики не найдены | Исправить ключ/свежесть map-cache, измерить запросы, проверить планы и добавить только нужные индексы |
| Batch writes/shards/async writes | Сборщик вызывает upsert на каждую запись; WAL включён; shard-ов нет | Одна короткая транзакция на подготовленную порцию; shard не вводить |
| Real-time | REST; backend WebSocket/SSE не обнаружены | Оставить REST/polling; при требовании push начать с SSE |
| Очереди/воркеры | FastAPI BackgroundTasks, без durable queue | Локальный отдельный scheduler/worker с lock и статусом, если необходима надёжная периодика |
| Повторы/backoff/circuit breaker/idempotency | Upsert по ID частично идемпотентен; сетевые таймауты/обработка ошибок есть; систематические retry/backoff/jitter и breaker не подтверждены | Ограниченные retry transient ошибок с backoff+jitter, run status; breaker позже при реальной серии сбоев |
| CQRS | Не обнаружен | Не внедрять до измеримого ограничения единого хранилища |
